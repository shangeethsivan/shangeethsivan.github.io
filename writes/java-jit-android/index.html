Just-in-time compilation

Plain-language notes on Java bytecode, native code, and Android. Also: Basic running warm-up guide.

What JIT is

A just-in-time (JIT) compiler turns Java bytecode into native machine code while your program is running, focusing on the methods that actually get called often. Code that stays cold can keep running in the interpreter.

That is different from a full ahead-of-time (AOT) compile, where the toolchain builds machine code for (almost) everything before you launch the app.

Why that is faster

Interpreting every bytecode instruction one by one is flexible but slow for hot loops and UI paths. Compiling the entire app up front can mean long installs and startup work, and the compiler never sees which branches you really take on your device.

JIT spends compile time on hot paths. After a method is compiled, later calls can run as native code instead of going back through the interpreter every time.

How Android uses it

The Android Runtime (ART) — the default from Android 7 (Nougat) onward — mixes JIT and AOT. Early runs collect profile data about which methods are hot. When the phone is idle and charging, ART can AOT-compile those hot methods using that profile (profile-guided compilation).

The next time you open the app, those paths can start from machine code already on disk. JIT still covers new code paths or methods that become hot after an update.

What that means on a phone

After an app “warms up,” you spend less time stuck in the interpreter on the paths you use most. Install is not a full AOT compile of every method in the APK, so first install stays lighter than compiling everything blindly on day one.

Updates and rarely used code are not all forced through the same upfront compile budget — the runtime adapts to how you actually use the app on that device.
